# AI Animated YouTube Shorts Studio

## What This Is

A local Next.js + TypeScript tool that turns a simple story idea (typed in Bangla or Banglish) into a complete original animated YouTube Short's worth of assets: an AI-written story with character/style bibles, a 5-7 scene breakdown, AI-generated scene images, and AI image-to-video clips — ready for manual assembly (voice, music, captions) in CapCut. Built for one non-technical user (the requester's wife) running it on her own Windows laptop.

## Core Value

One simple idea in → one genuinely original, structurally-unique animated episode's worth of local video assets out, without ever exceeding the $15 experiment budget or silently shipping a story that's a thin reskin of a previous one.

## Business Context

- **Customer**: The requester's wife — sole user, exploring whether an AI-animated YouTube Shorts channel is viable.
- **Revenue model**: YouTube ad monetization on original, AI-assisted animated Shorts (not built by this tool — this MVP only produces the raw clips; publishing and monetization happen manually, outside this tool).
- **Success metric**: Whether the concept is worth continuing past Month 1 — measured by whether the tool reliably produces structurally-original, usable episodes within budget, not by view counts (out of scope for this tool).
- **Strategy notes**: Full YouTube-policy reasoning (why the uniqueness system exists, what counts as "AI slop" to avoid) came from the requester's original build brief, provided in chat and not duplicated here.

## Requirements

### Validated

- ✓ Wife can type a story idea in Bangla or Banglish and get a coherent original story back — Phase 2 (STORY-01/02; Banglish confirmed coherent on every real attempt, Bangla confirmed coherent on 3 independent ideas; the one open thread is that no single idea has a completed same-idea side-by-side comparison in both scripts yet — carried into Phase 3/4, not a sign of an actual quality gap)
- ✓ Every story ships with a Character Bible, Style Bible, and 5-7 scene plan generated automatically — she never writes or sees raw prompts — Phase 2 (STORY-03/04/05, SCENE-01/02; real 5-scene run produced both bibles plus a numbered scene plan with no gaps/duplicates, and character appearance carried consistently across all 5 independently-generated images)
- ✓ New stories are checked for structural similarity against all past stories (not just noun-swapping) and rejected/regenerated if too similar, up to a capped number of attempts — Phase 3 (UNIQUE-01/02/03; a deterministic three-element pre-filter plus an LLM tie-breaker for borderline cases, proven against a real generated story: a mechanical near-duplicate correctly rejected, a surface-word-only lookalike correctly passed)
- ✓ All stories, scenes, and generation records persist in local SQLite and survive an app restart — Phase 3 (PERSIST-01; proven via genuine separate-OS-process restarts, both on fixture data and on a real Gemini-generated story)
- ✓ Scene images generate before any video spend, with a mandatory human approval checkpoint, and any single scene's image can be regenerated without touching any other scene's image, video, or status — Phase 4 (APPROVAL-01, IMAGE-02)
- ✓ Approved scenes animate via Veo 3.1 Lite image-to-video (9:16, 720p, 4/6/8s), with independent per-scene status, retry, and progress display, surviving an app restart — Phase 2 proved the single-scene path (VIDEO-01); Phase 3 added restart-survival (VIDEO-03); Phase 4 completed full-episode batch dispatch and per-scene retry (VIDEO-02/04)
- ✓ Every paid generation call — story, uniqueness check, image, or video, first attempt or retry — is checked against a configurable hard monthly budget ($15 default) before it fires, with no bypass via retry; she can see running spend by type against the limit — Phase 5 (BUDGET-01 through BUDGET-05). The Phase 2-3 dev-testing ceiling (`DEV_CEILING_USD`) is retired from every wife-facing path; it survives only as a separate, explicitly-labelled ceiling for direct-provider CLI probe scripts, since two of the four probe scripts route through the same real gate regardless
- ✓ Finished episode assets land in a predictable local folder structure, correctly numbered for CapCut import, and she can browse and open any past story from a Story Library — Phase 4 (OUTPUT-01, OUTPUT-03, LIBRARY-01)
- ✓ A provider failure (error, timeout, rate limit, malformed response) is caught, shown to the wife in plain language, and leaves the affected scene in a clearly failed-but-retryable state without corrupting other scenes' data — Phase 6 (RELIABILITY-01; differentiated block/technical/timeout messaging across all three providers, a bounded timeout on every provider HTTP call including the one the phase's own security audit found missing, and a server-anchored stuck-generation clock that survives a page reload)
- ✓ API keys and other secrets never reach client-side JavaScript, logs, or story metadata, and the app starts cleanly with a missing key instead of crashing — Phase 6 (SECURITY-01, STARTUP-02; `assertApiKeyConfigured()` as the literal first statement of every gated dispatch function, path-scoped log redaction, and an automated 5-check secrets-hygiene gate appended to the test suite)
- ✓ Every saved video file is a genuinely playable MP4 at the requested duration and dimensions, never a mislabeled error response — Phase 6 (OUTPUT-02; real MP4 container/duration/aspect validation before any scene is ever marked READY, with a same-phase security audit closing the one path that could still reach READY unvalidated)

### Out of Scope

- Automated voice/music/SFX/caption generation — she adds these manually in CapCut
- Automated YouTube publishing — manual upload
- Authentication, multi-user support, cloud hosting, SaaS billing — single local user, single machine
- Redis, PostgreSQL, Kubernetes, n8n, complex job queues/microservices — unjustified complexity for a single-user local experiment
- Vector database for uniqueness checking — a cheap deterministic pre-filter plus a targeted LLM comparison is sufficient at this scale
- Reference-image and video-extension features of higher Veo tiers — the image-first workflow doesn't depend on them

## Context

- The requester supplied an extremely detailed build brief (externally authored via ChatGPT) covering architecture, data schema, UX flow, and a 34-item acceptance test checklist (AT-01 through AT-34). That brief is the primary spec — it was verified against current facts during brainstorming rather than re-derived from scratch.
- Provider facts verified against official docs during brainstorming (September 2026): Veo 3.1 Lite is model id `veo-3.1-lite-generate-preview`, priced at $0.05/sec at 720p and $0.08/sec at 1080p, still in paid preview status. Image-to-video, 9:16, and 4/6/8-second durations are confirmed; reference-image and video-extension features are not supported on this tier (expected — the image-first workflow doesn't need them). Imagen 4 is already deprecated (shut down August 2026), so image generation uses Gemini's native image models instead.
- A real commercial-terms nuance was surfaced and consciously accepted rather than ignored: the Gemini Developer API's Additional Terms of Service bar "API Clients... directed towards or likely to be accessed by individuals under 18." Judgment call made with the requester: the private, single-adult-operated local generation tool (not the downstream YouTube channel it feeds) is the "API Client" in the ToS sense. Proceeding on that reading rather than moving to Vertex AI, which would remove the ambiguity at the cost of a heavier setup (GCP project, billing account, service account credentials instead of one API key).
- Single-provider architecture: Google Gemini Developer API, one AI Studio API key, used for the LLM (Story Director), image generation, and video (Veo 3.1 Lite) alike — chosen over spreading across providers for simplicity of billing and budget tracking.
- At the time of planning, the requester had a Google account but had not yet created the AI Studio API key or enabled billing — expected to complete that in parallel with early implementation.
- Phase 2 surfaced a real, unanticipated content-safety finding: the same benign story idea, sent to Gemini's Story Director in native Bangla script, was blocked by the safety classifier 3 out of 3 times before any generation began, while the identical idea in Banglish (romanized Bangla) succeeded. A second, different idea then succeeded in Bangla script on the first attempt with zero retries — so the block tracks specific wording (the first idea involved a child handling an inherited object "secretly") rather than Bangla script itself being inherently riskier. This is the opposite of what pre-implementation research hypothesized (that Banglish, not Bangla, would be the more failure-prone script) and is worth keeping in mind for Phase 3/4 prompt design: neither script can be assumed "safer" by default.
- Phase 2's dev-testing spend ledger (`DEV_CEILING_USD`, a $3.00 throwaway cap separate from the real `MONTHLY_BUDGET_USD` system) finished the phase at $2.9370 of $3.00 — only $0.063 headroom remains. Any further real paid probing during Phase 3/4 development against this same ledger needs either a deliberate, explicit increase to `DEV_CEILING_USD` or a fresh dev ceiling — raising it to route around a refusal remains prohibited, but the requester consciously choosing to raise the constant ahead of time for a specific testing need is a different, legitimate action.
- That exact scenario happened in Phase 3: with $0.013 headroom left and two live-browser UAT checks still needing real paid calls, the requester explicitly named a new figure ($3.25) rather than Claude inferring one. Both the source constant (`spend-ledger.ts`) and the already-persisted ledger file's own `ceilingUsd` field needed updating — the latter is what `checkCeiling` actually reads at runtime, so changing only the source constant would have silently done nothing.
- Phase 3 surfaced a real bug caught before it ever ran against real data: the researched uniqueness-comparison design would have tokenized Bangla-script text with an ASCII-only character class, silently collapsing it to an empty token set and scoring empty-vs-empty as 1.0 ("identical") — a false-collision trap for the product's primary input language. The planner caught this from the research alone and mandated a Unicode-aware tokenizer, English-only abstracted fingerprint fields, and empty-set-scores-0 semantics; a real Bangla-script test fixture and a real generated story both confirm the fix holds.
- Also from Phase 3: resubmitting the *exact same* story idea text a second time did **not** reliably reproduce a structural collision — the Story Director's real creative variation between generations can produce different enough abstracted fingerprints that two runs of one idea don't always 3-of-3 match. Forcing a specific uniqueness outcome (e.g. for testing) is therefore non-deterministic and shouldn't be assumed cheap or guaranteed.
- **v1.0 shipped state**: ~25,300 lines of TypeScript across `src/`, 249 commits, 6 phases / 26 plans / 33 requirements, all fully verified (code review + security audit + phase-goal verification + UAT on every phase). Real cumulative spend across the whole milestone (Phase 1's provider proofs through Phase 6's zero-cost closing checkpoint): $5.0720 of the $15.00 budget — the tool has never come close to its own hard ceiling in practice. Known, deliberately-accepted residual items carried forward rather than fixed: `check-boundaries.ts`'s newer invariants are textual/substring checks, not full control-flow analysis (06-REVIEW.md WR-04); a persistent (not one-off) video download failure can let a scene's 3-attempt retry cap go unenforced, though the real $15 budget ceiling remains the unaffected backstop either way (06-SECURITY.md AR-05); and D-04's original full-scale (5-6 scene) Bangla-script proof run was blocked 3/3 times on one specific idea's wording in Phase 2, later independently satisfied by a different idea in quick task 260913-4rr, so the specific original attempt was never retried to success.

## Constraints

- **Budget**: $15 USD hard total cap for Month 1 (configurable via `MONTHLY_BUDGET_USD`), target actual spend $8-10. Every paid provider call must pass a pre-flight `current_month_spend + estimated_request_cost <= monthly_budget` check — no exceptions, no bypass via retry.
- **Tech stack**: Next.js (App Router) + TypeScript + SQLite (via Prisma) + local filesystem only, single process, started with one local command. Explicitly no separate backend service, no cloud infrastructure, no n8n.
- **Timeline**: Originally scoped as a roughly-24-hour golden-path MVP push. The requester explicitly chose full GSD process rigor (research, planning, code review, security audit, verification, UAT at every phase) over that original deadline once it became clear both couldn't be had together — v1.0 actually shipped across 2026-09-12 to 2026-09-22 (6 phases, 26 plans, ~10 days) as a result. The golden-path scope itself (idea → reviewed story → approved images → generated videos → local MP4s ready for CapCut) is unchanged; only the speed-vs-rigor tradeoff was renegotiated, deliberately, mid-project.
- **Commercial-use**: All generated assets must be commercially usable for a monetized YouTube channel — verified per-provider against current terms, never assumed from "an API exists" or "there's a free tier."
- **Platform**: Must run locally on the requester's Windows laptop with a single documented start command; no developer environment expected on the user's (wife's) side.

## Key Decisions

| Decision | Rationale | Outcome |
|----------|-----------|---------|
| Single provider: Google Gemini for LLM + image + Veo 3.1 Lite | One API key and billing account, simplest possible budget tracking, still clears the cost/commercial/capability bar | ✓ Good — Phase 1 proved image gen + Veo image-to-video work end-to-end from one API key, real cost $1.2010 across 6 calls |
| Plain Gemini Developer API key, not Vertex AI | Faster setup; "API Client" in the ToS is judged to be the private local tool, not the YouTube channel | ✓ Good — no access/permission issues encountered in Phase 1's real calls |
| No ffmpeg, no in-app audio stripping | Veo's MP4 passes through as-is; audio gets muted/replaced manually in CapCut as originally planned — avoids a native binary dependency for a 24-hour MVP | — Pending (not yet exercised — CapCut import happens in a later phase) |
| Prisma as the ORM | Best Next.js/TypeScript developer experience for a single-developer local SQLite app: migrations, a type-safe client, and Prisma Studio for manual DB inspection while debugging | ✓ Good — Phase 3 proved real cross-process restart-survival on Windows with Prisma 7's driver-adapter architecture (`@prisma/adapter-better-sqlite3`, no Rust query engine), pinned exactly to 7.10.0 after discovering `prisma`'s `latest` npm tag resolves to an unrelated 8.0.0 release candidate |
| Deterministic pre-filter + targeted LLM call for uniqueness, no vector database | Cheap and instant for the obvious cases; the LLM is only spent on borderline-similar candidates; avoids infrastructure the project doesn't need | ✓ Good — Phase 3 proved this against a real generated story: a mechanical near-duplicate scored 0.778-0.875 on all three elements and correctly rejected without any LLM call; a surface-word-only lookalike scored 0.050-0.059 and correctly passed |
| No automated test suite; rely on the acceptance-test checklist plus targeted unit tests for budget math and uniqueness scoring | Disproportionate effort for a 24-hour single-user MVP; the requester's own AT-01 through AT-34 checklist is the real verification gate | ✓ Good — Phase 1 followed exactly this pattern (19 targeted unit tests for spend-ledger/log-response, no framework), independent verifier + code review both passed |
| `MONTHLY_BUDGET_USD` stays exactly $15, despite a real RM/USD mismatch discovered during Phase 1 execution (50 RM funded ≈ $11-12 USD at current rates, 80 RM eventual top-up ≈ $18-20 USD — neither matches $15 cleanly) | Requester's explicit choice: keep the originally-speced figure rather than resync to either the currently-funded or eventual-total RM amount; the app's own spend ledger (not Google's Billing API — real-time, zero-lag, and the actual enforced gate) is what checks against this number, so the mismatch is a funding-cushion question, not a code-correctness one | ✓ Good |
| No Google Cloud Billing API polling for live remaining-budget display | Billing data has an inherent multi-hour-to-day lag (aggregation pipeline, not real-time), so it would be a strictly weaker signal than the app's own zero-lag internal ledger if used as a gate — and reading real billing data needs billing-account-level IAM/service-account setup, a meaningfully bigger lift than an API key. The GCP billing alert already recommended during provider setup serves the same "catch drift against Google's real numbers" purpose via email, without the lag problem or the extra permissions | ✓ Good |
| Motion prompts for Veo must avoid requesting character pose changes (turning, looking, reaching, walking, gesturing) — favor camera drift and environmental motion (pulsing/glowing effects, particle drift, breeze-driven cloth/hair sway) instead | Phase 1's D-01 representative probe surfaced a real kinematic-coherence defect: a mild "the girl looks around for her cat" motion prompt caused Veo 3.1 Lite to animate the head turning backward while the torso stayed front-facing (user-reported "horror" effect). A quick follow-up probe (260912-j3x) with a conservative, pose-static motion prompt on the same image confirmed the artifact does not reproduce while the clip remains visibly animated (not a frozen still) | ✓ Good — validated by a real $0.40 Veo call, not assumed. Binding constraint for Phase 2's Story Director motion-prompt generation, then reconfirmed in Phase 2: two real Story-Director-authored motion prompts, both watched by the requester, showed no artifact |
| Every `recordSpend` call after a dispatched paid call must record `billed: true` unconditionally, never conditioned on whether the local process could observe a successful result (e.g. a file being written) | Phase 2's code review (CR-01) caught `generate-video.ts` marking a client-side Veo polling timeout as `billed: false` — the opposite of the project's own conservative-accounting convention, since Veo may have billed the dispatched operation regardless of what this process observed afterward. Fixed to match the pattern `director.ts`/`generate-images.ts` already used correctly | ✓ Good — carried forward unchanged into Phase 5's real budget system |
| Carry the $5.072 of Phase 1-4 dev-testing spend forward into the real budget, rather than starting it at $0 | PROJECT.md itself frames the dev ceiling as "carved out of the real $15 total... not additional to it" — her first real story should be generated against the true remaining headroom (~$9.93), not a fresh $15 | ✓ Good — the requester's own decision; a reconciling importer matched 14 already-dual-written entries against the dev ledger's 40 and imported only the 26 unmatched ones, reaching exactly $5.0720 with no double-count |
| No Google Cloud Billing API polling for the real budget's month-to-month figure either — the requester sets/changes each month's number himself, with unused amounts rolling over | Extends the Phase 1 decision (same lag/permissions reasoning) to the production budget: a requester-set figure with app-internal rollover is zero-lag and needs no new GCP permissions, and is what "$15 first month, maybe $10 second month" actually requires | ✓ Good |
| A single app-wide `serializeDispatch` promise-chain mutex gates every paid dispatch (story, uniqueness check, image, video) — the budget check, the provider call, and the spend-record write all happen inside one serialized unit, not just the check | Phase 4's code review had already closed this exact TOCTOU race for video alone (a promise-chain mutex around `generateSceneVideoAction`); Phase 5 generalized that proven pattern app-wide rather than inventing a heavier reserve-then-commit ledger schema, once real money (not a dev ceiling) was on the line for every call type | ✓ Good — `dispatch-chain.test.ts` proves two calls in the same tick never overlap; the app-wide generalization is a documented, deliberate widening of Phase 4's blast radius, not an oversight (see 05-REVIEW.md WR-01 for the one residual gap: no per-call timeout, deferred to Phase 6) |
| Spend records are written at the moment of dispatch (with a null story id when the story doesn't exist yet) and only *linked* to a story afterward, rather than accumulated and flushed after a successful save | A blocked, unparseable, or unsaveable story was still a real, billed dispatch — flushing only after a successful save would have silently dropped that spend from the new authoritative ledger forever. `GenerationRecord.storyId` relaxed to nullable to allow this | ✓ Good — closes a real gap the Phase 5 planner caught by reading `create-story.ts` directly rather than trusting the research's original design |
| Every Google GenAI SDK call site must set an explicit `httpOptions.timeout`, structurally enforced by a build-time check | The shared `serializeDispatch` queue (Phase 5) has no timeout of its own — one hung provider call would otherwise wedge every future paid dispatch app-wide until a manual restart, not just the one caller | ✓ Good, with one correction — Phase 6's security audit found the video download call (`ai.files.download()`) was the one call site the original sweep missed, since it isn't a `generateContent`-style call; fixed with an external `Promise.race` wrapper rather than the SDK's own timeout option, after empirically confirming the SDK's own abort doesn't actually unblock a stalled download on this specific call (see the audit-trail note below) |
| A local save/readback failure after a successful paid generation grants a one-shot free retry (D-05) instead of consuming one of the scene's limited attempts, for both images and video | The provider call already succeeded and already cost real money — a transient local I/O problem (locked file, antivirus scan, a stalled download) is a different failure category from a genuine generation failure (D-02) and must not be billed twice, once in money and once in her limited retry budget | ✓ Good — Phase 6 (06-04) proved this for validation failures and readback failures; the same phase's own security audit later found and closed one more path (an unbounded, previously-unvalidated readback-failure branch) that had fallen outside this rule by predating OUTPUT-02's validation step entirely |
| A same-phase security audit is worth running even when a first-pass self-review already looks clean, and a second, independent re-check of that audit's own fix is worth running too | Phase 6's own code-review pass (self-classified) found nothing wrong with the video pipeline; an independently spawned security audit then found two genuine high-severity gaps a text-pattern review couldn't have caught (an unbounded provider call, an unvalidated status write). The FIX for one of those two was itself then found to misdescribe the installed SDK's actual behavior by a second, independent audit pass — the fix's real-world effect was still correct, but for a different mechanism than first documented, confirmed only by writing and running a probe script against the actual SDK source rather than trusting either the SDK's documentation shape or a first read of its code | ✓ Good — full audit trail in `06-SECURITY.md`; nothing here was taken on a single pass's word |
