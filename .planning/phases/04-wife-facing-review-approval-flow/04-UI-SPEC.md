## Design System

| Property | Value |
|----------|-------|
| Tool | none |
| Preset | not applicable |
| Component library | none — plain Tailwind utility classes directly in JSX, no headless/primitive library (no Radix, no Base UI) |
| Icon library | none — no icon library is installed or used anywhere in the codebase (verified: no `lucide-react`/`heroicons`/`react-icons`/`@radix-ui/react-icons` import exists). Do not add one this phase. Status/state is conveyed by text label + color only, matching the existing convention. If a visual affordance beyond text/color is genuinely needed (e.g. an "approved" mark), use a plain Unicode glyph (e.g. `✓`) rather than a new dependency. |
| Font | Geist Sans (`next/font/google`), bound to `--font-geist-sans` and applied via Tailwind's `font-sans` utility (`src/app/page.tsx`'s root wrapper). `globals.css`'s `body { font-family: Arial, Helvetica, sans-serif }` is a vestigial scaffold default superseded by `font-sans` in practice — do not treat it as the active font. Geist Sans has no Bengali glyphs; the browser silently falls back to the OS's default Bengali-capable font for any Bangla-script text (the story idea/character description she types, and any Bangla content the model returns). This is existing, already-working behavior — no action needed this phase. |

### Why `Tool: none` (not a fresh shadcn init)

The phase-launch context is explicit that this phase must extend the plain-Tailwind visual language already shipped across Phases 2–3 (`CreateStoryForm.tsx`, `StoryReview.tsx`, `SceneCard.tsx`, `SceneVideo.tsx`), not introduce a new one. `components.json` does not exist and no shadcn/component-library dependency is installed (`package.json` confirms only `next`, `react`, `tailwindcss`). Introducing shadcn now would create two competing visual languages across a 4-5-screen flow with one day of budget left. This is treated as pre-decided by the upstream context, not re-asked of the user.

## Screen Inventory (Phase 4)

The existing 3-screen state machine (`create` → `review-story` → `review-images`) in `src/app/page.tsx` extends to 4 screens, plus an optional 5th (Library, soft/LIBRARY-01). All screens share the existing page shell: `flex flex-col flex-1 items-center bg-zinc-50 font-sans dark:bg-black`, content column `flex flex-1 w-full max-w-2xl flex-col gap-8 px-6 py-16`.

| # | Screen | Status this phase | Purpose | Key new elements |
|---|--------|--------------------|---------|-------------------|
| 1 | Create | unchanged | Typed idea → story | Add a low-emphasis "My Stories" nav link (LIBRARY-01, soft) — see Copywriting Contract |
| 2 | Review Story | unchanged | Read story/bibles/scene list | none |
| 3 | Review + Approve Images | **extended** | Review per-scene images, regenerate a single scene, approve the whole set | Per-scene "Regenerate this image" action; single story-level "Approve These Images" action; post-approval confirmation + "Continue to Video Generation" nav |
| 4 | Video Status (**new**, D-05) | **new** | Watch every approved scene's video job, retry a single failed/capped scene, reach the output folder | "Generate All Videos" trigger; one card per scene reusing `SceneVideo`'s states + a new "retry-limit-reached" state; polled status; "Open Output Folder" once complete |
| 5 | My Stories (**new, soft**, LIBRARY-01) | **new, soft** | See past stories, open one to view | List rows: title, date, computed status, scene count; empty state |

Screen 4 reuses Screen 3's existing grid (`grid grid-cols-1 gap-4 sm:grid-cols-2`) and reuses the already-built `SceneVideo` component's four states (`waiting`/`generating`/`ready`/`failed`) directly as each row's content, adding exactly one new state (`capped`) for the retry-limit-reached case. This is a deliberate minimal extension, not a new visual system.

## Spacing Scale

Declared values — this is the codebase's **actual, already-shipped** scale (Tailwind v4 default, 4px increments), not a fresh 8-point proposal. Every value is a multiple of 4.

| Token | Value | Usage (verified in existing components) |
|-------|-------|---------|
| 3xs | 4px | `gap-1`, `py-1` — tightest inline spacing (e.g. video-ready block) |
| xs | 8px | `gap-2` — card internal stack spacing (`SceneCard`) |
| sm | 12px | `p-3` / `px-3` / `py-3` — card padding, primary button vertical padding, small pill button horizontal padding |
| md | 16px | `gap-4` — grid gaps between scene cards |
| md+ | 20px | `gap-5` / `px-5` — form field stack gaps, primary button horizontal padding |
| lg | 24px | `gap-6` / `px-6` — screen 3's outer content stack, page horizontal padding |
| xl | 32px | `gap-8` — top-level section stacks (`CreateStoryForm`, `StoryReview`, page `<main>`) |
| 3xl | 64px | `py-16` — page-level vertical padding |

Exceptions: none — every value already in use satisfies this contract's own multiples-of-4 rule. New Phase 4 UI (Screen 4, the approval controls, the Library list) must reuse these exact tokens, not introduce a new increment (e.g. no `gap-3`/`gap-7`).

## Typography

The codebase already uses 5 distinct sizes across 3 weights — more than the usual 3-4-size/2-weight guideline, but this is the established, already-shipped scale from Phases 2-3 and must be preserved for consistency rather than normalized mid-flow. Phase 4's new UI (Screen 4, approval controls, Library) reuses these exact 5 tokens; do not introduce a 6th size or a 4th weight.

| Role | Size | Weight | Line Height | Usage |
|------|------|--------|-------------|-------|
| Display | 24px (`text-2xl`) | 600 semibold | 1.2 | Screen-level titles: story title, "Create New Story" |
| Heading | 18px (`text-lg`) | 500 medium | 1.3 | Section subheadings: "Character Bible", "Style Bible", "Scenes" |
| Body | 16px (base, no size class) | 400 regular | 1.5 | Story paragraph text, scene-card header ("Scene N") at weight 500 as the one exception (see note) |
| Label | 14px (`text-sm`) | 500 medium | 1.4 | Form field labels, `<dt>` terms |
| Small / Caption | 12px (`text-xs`) | 400 regular (status badges, hints, video/failure messages) or 500 medium (small pill button labels) | 1.4 | "Waiting"/"Image ready" badges, `SceneVideo` messages, "Try again" / "Regenerate this image" button text |

Note: `SceneCard`'s "Scene N" header uses Body size (16px) at weight 500 (medium), not 400 — this is the one place Body and Label weights mix at the same size. Preserve it exactly for Screen 4's per-scene card headers rather than inventing a new combination.

## Color

This is a deliberately monochrome-first palette: the "accent" is an inverted foreground/background pair, not a saturated brand color. Two semantic colors exist beyond it — red for hard failures, amber for calm/non-alarming limit-reached messaging (Phase 3's established precedent).

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `bg-zinc-50` (`#fafafa`) light / `bg-black` (`#000000`) dark | Page background (all screens) |
| Secondary (30%) | `bg-zinc-100`/`#f4f4f5` (light) `bg-zinc-900`/`#18181b` (dark) fills; `border-zinc-300`/`#d4d4d8` (light) `border-zinc-700`/`#3f3f46` (dark) borders | Card/well surfaces: scene image/video placeholder wells, `SceneCard` borders, form input borders |
| Accent (10%) | `bg-foreground` (`#171717` light / `#ededed` dark, inverted) with `text-background` | **Reserved for exactly one element per screen: that screen's single primary call-to-action button** — "CREATE STORY", "Generate Scene Images", "Approve These Images" (new), "Continue to Video Generation" (new), "Generate All Videos" (new), "Open Output Folder" (new), "Create Your First Story" (new, Library empty state). Never used for a secondary/per-scene action. |
| Destructive / error | `border-red-300 bg-red-50 text-red-800` light / `border-red-800 bg-red-950 text-red-200` dark (banners); `text-red-700` light / `text-red-300` dark (inline failure text) | Hard failures: create-story error, image/video generation error banners and inline messages |
| Warning / calm-exhaustion | `border-amber-300 bg-amber-50 text-amber-900` light / `border-amber-800 bg-amber-950 text-amber-200` dark | Non-alarming limit-reached / heads-up messaging: Phase 3's uniqueness-exhaustion banner, and this phase's new retry-cap-reached and post-approval-regeneration heads-up messages (D-03) |

Accent reserved for: the single primary/terminal action button on each screen, never for secondary per-scene actions ("Regenerate this image", "Try again"), never for the "My Stories" nav link, and never as a background fill.

### Screen 4 per-scene status label vocabulary

Reuses `SceneVideo`'s existing state labels/messages exactly, adding one new state:

| State | Label / message |
|-------|------------------|
| waiting | (no label shown until dispatch; before "Generate All Videos" is pressed, rows show nothing extra) |
| generating | "Generating video... this can take a few minutes." *(reused verbatim)* |
| ready | inline `<video>` player, no extra text *(reused verbatim)* |
| failed | failure message + "Try again" button *(reused verbatim)* |
| **capped (new)** | Uses the "scene video retry cap reached" copy above, in the amber inline style, **no button** (retries exhausted — nothing left to offer but the explanation) |

### Library computed status label vocabulary (LIBRARY-01)

Per RESEARCH.md's recommendation, `Story.status` is a computed label (not a new stored enum) derived from `uniquenessStatus` + `imagesApprovedAt` + scene video statuses:

| Label | Condition |
|-------|-----------|
| "Draft" | Story created; images not yet all ready |
| "Ready to Approve" | All scene images ready; `imagesApprovedAt` still null |
| "Generating Videos" | `imagesApprovedAt` set; at least one scene not yet in a terminal video state |
| "Complete" | Every scene's video is Ready |
| "Needs Attention" | At least one scene is permanently `capped` (failed + retry cap reached) and no scene is still generating |
